# CT002 / CT003 Steering & Balancing

The CT002/CT003 emulator speaks Marstek's native CT protocol. Use it when you
steer **multiple** storage devices: it coordinates one shared target across the
fleet instead of letting each battery react on its own. This page covers the
`[CT002]` / `[CT003]` configuration section, active steering, multi-battery
balancing, and efficiency optimization.

For the UDP wire protocol, see
[ct002-ct003-protocol.md](ct002-ct003-protocol.md).

## Basic configuration

```ini
[CT002]
# CT type is derived from the emulated device (ct002 -> HME-4, ct003 -> HME-3).
# CT MAC (12 hex digits, from Marstek app).
# If empty, the emulator accepts any request CT MAC and echoes the request’s
# CT MAC in responses. If set, the emulator responds only to that CT MAC.
CT_MAC = 001122334455
# UDP port to bind for CT002/CT003 (default 12345).
UDP_PORT = 12345
# WiFi RSSI reported to the storage system
WIFI_RSSI = -50
# Ignore repeated requests from the same consumer within this window (seconds).
# Also supported by the Shelly emulator (keyed by battery IP); set it under
# [GENERAL] to apply regardless of the emulated device type.
DEDUPE_TIME_WINDOW = 0
# Forget consumers after this many seconds without updates (multi-consumer support).
# Unset (default): adaptive — a battery is dropped after missing ~2 of its own
# poll cycles (min 5s), like the real CT. Set a number for a fixed window.
CONSUMER_TTL = 120
```

## Active steering, balancing & efficiency

All keys in this section go under the `[CT002]` or `[CT003]` section. They are
**not** read from `[GENERAL]` or from powermeter sections:

- **ACTIVE_CONTROL** — When true (default), the emulator smooths the grid
  reading, splits the target across batteries, and balances their load. When
  false, the emulator relays raw meter values and the batteries decide for
  themselves.

### Fair distribution — balancing load across multiple batteries

- **FAIR_DISTRIBUTION** (default true) — Adjust each battery's target so they
  share the load evenly. Only matters with two or more batteries. To split
  *unevenly* (e.g. give a larger battery a bigger share), set a per-battery
  **Distribution Weight** from Home Assistant. See
  [Per-battery controls](mqtt-insights.md#per-battery-controls-home-assistant-entities).
- **BALANCE_GAIN** (default 0.2) — How hard to correct imbalance between
  batteries. 0.0 = no correction (equal split only); 0.3–0.5 = faster
  rebalancing, but it may overshoot.
- **BALANCE_DEADBAND** (default 25 W) — Ignore imbalance smaller than this. It
  stops micro-corrections when the batteries are already close. It sits above the
  battery firmware's own ±20 W input deadband, so a correction the firmware would
  ignore is never sent.
- **MAX_CORRECTION_PER_STEP** (default 80 W) — Cap on the per-cycle balance
  correction. It limits how far one battery's target can move from its fair
  share in a single step.
- **ERROR_BOOST_THRESHOLD** / **ERROR_BOOST_MAX** (defaults 150 W / 0.5) — Once
  the imbalance passes the threshold, the balance gain is multiplied by up to
  (1 + ERROR_BOOST_MAX). With the defaults, effective gain rises from 0.2 to at
  most 0.3 at ≥ 150 W imbalance. Large imbalances then close faster.
- **ERROR_REDUCE_THRESHOLD** (default 20 W) — Below this imbalance, the gain
  scales down in proportion. Corrections get gentler as the batteries approach
  equilibrium.
- **MAX_TARGET_STEP** (default 0 = unlimited) — Maximum change in a battery's
  target relative to its current output. A hard clamp on per-cycle change.
- **PACE_BASE_STEP** / **PACE_MAX_STEP** (defaults 30 W / 100 W) — Ramp pacing
  for the auto control loop. Each battery's per-poll command delta is capped. The
  cap starts at the battery firmware ramp's first step and grows toward the max
  only while the battery clearly follows the command. That keeps the firmware's
  accelerating internal ramp from overshooting on meter latency.
  `PACE_BASE_STEP = 0` disables pacing.
- **IMPORT_TRIM_W** (default 15 W) — Steady-import trim. In steady state, every
  Marstek firmware leaves the grid a few watts on the *import* side of zero. So
  you keep buying, at the retail tariff, household load the battery could supply.
  Once the grid has held steady for a few polls, the batteries are nudged to
  cover it, while staying clear of a full or empty pack. It never trims during a
  load step, so it adds no overshoot. `0` disables it.

### DC battery keep-alive

Applies to each DC-only battery on its own. It works with a single battery too,
independent of balancing:

- **MIN_DC_OUTPUT** (default 0 = disabled) — Minimum discharge in watts. It keeps
  a DC battery's inverter from switching off at 0 W and falling asleep under high
  PV surplus (a known behaviour of the Marstek B2500). It applies to each DC-only
  battery that has no inverter of its own; AC batteries (Venus) and Jupiter are
  unaffected. You can also set it per battery from Home Assistant (see
  [Min DC Output](mqtt-insights.md#per-battery-controls-home-assistant-entities)).
  Use at least 20 W.

### Battery efficiency optimization

Concentrating power on fewer batteries, probing handoffs, and swapping away from
ones that cannot follow.

Batteries have a minimum operating power. Below it, their DC-DC converter
efficiency drops sharply. When several batteries split a small load, each one may
run in that inefficient range and waste energy as heat. The efficiency
optimization spots this and concentrates the load on fewer batteries, so each
stays above its efficient minimum and the rest idle. Batteries rotate now and
then, so wear is shared evenly.

> **Not recommended for DC batteries.** Efficiency rotation needs to steer a
> deprioritized battery's output down to 0 W. The CT002 protocol cannot command
> DC-coupled batteries such as the Marstek B2500 to 0 W: they keep running at
> their minimum output power (e.g. ~80 W). Idling them does not work, so the
> feature gains you nothing. It is meant for AC batteries (e.g. the Marstek
> Venus), which you can steer all the way to 0 W. On DC batteries, leave the
> efficiency settings below disabled.

When a timed rotation or forced swap promotes a new battery, the handoff uses a
**probe phase**. It does not drop the previous active battery to zero right away.
During the probe, the promoted battery gets the real CT002 delta-control signal.
The previous active battery (or batteries) stays online as backup and covers the
signed residual shortfall, based on the promoted battery's latest reported power.
Once the promoted battery shows meaningful real output, the probe commits and the
backup fades out. If it never ramps, the probe times out and the balancer
restores the previous active battery. After a successful probe, saturation
detection stays active, so mid-interval failures still trigger a swap.

- **MIN_EFFICIENT_POWER** (default 0 = disabled) — When the per-battery share of
  total demand falls below this threshold (watts), spare batteries are
  deprioritized so the rest run above their efficient minimum. Example: 2
  batteries, 200 W demand, threshold 150 → one battery gets 200 W, the other
  idles. Hysteresis (×1.2) stops oscillation at the boundary.
- **EFFICIENCY_ROTATION_INTERVAL** (default 900 s, minimum 10) — Seconds between
  rotating which battery has priority. It keeps wear even across batteries.
- **EFFICIENCY_FADE_ALPHA** (default 0.15) — EMA factor for how fast batteries
  hand over during efficiency switchovers. It mainly sets how fast the old
  battery fades out **after a successful probe**, and it also smooths ordinary
  efficiency transitions. Lower values give smoother, slower transitions; higher
  values are faster. Set to 1.0 for instant switching.
- **EFFICIENCY_SATURATION_THRESHOLD** (default 0.4) — An active battery whose
  saturation score passes this value can't follow its target, because it is full,
  empty, or limited from outside. It is swapped out at once for a healthy
  deprioritized battery, rather than waiting for the next timed rotation. During
  a probe, the probe timeout is the main "never ramps" control. This threshold
  still matters after the probe succeeds, and for batteries that are already
  active. Set to 0 to disable. The saturation EMA is time-weighted, so batteries
  with slower powermeters (>10 s update interval) build up saturation faster per
  sample. If you see needless swaps with a slow powermeter, raise this value
  (e.g. to 0.8).
- **EFFICIENCY_DEMAND_ALPHA** (default 0.1) — EMA factor that smooths the
  household-demand estimate. That estimate decides how many batteries stay
  active, so smoothing stops meter noise from throwing a battery in and out of
  the pool every few readings. The regulation loop still acts on the raw grid, so
  tracking is unchanged. Lower is smoother, and slower to react to a real
  sustained load change; `1.0` disables it. It only matters with
  `MIN_EFFICIENT_POWER` set and two or more batteries.
- **SATURATION_DETECTION** (default true) — Track how well each battery follows
  its target. When a battery cannot deliver (full or empty), its share is cut and
  handed to the others.
- **SATURATION_ALPHA** (default 0.15) — EMA factor for the saturation score.
  Lower = slower to call a battery saturated, and slower to recover.
- **MIN_TARGET_FOR_SATURATION** (default 20 W) — Ignore saturation tracking when
  the target is below this value. This avoids false positives at low power. Probe
  success uses the same threshold.
- **SATURATION_GRACE_SECONDS** (default 90 s) — The longest **probe window** when
  a timed rotation or forced swap promotes a deprioritized battery. During this
  window, the previous active battery stays available as backup and covers the
  residual shortfall while the promoted battery ramps. If the promoted battery
  reaches meaningful output sooner, the probe commits early.
- **SATURATION_STALL_TIMEOUT_SECONDS** (default 60 s) — Stall escape for
  non-probe grace cases, such as a battery rejoining auto control after a pause
  or after manual mode. Probe handoffs themselves now use the full probe window
  above as their main timer.
- **SATURATION_DECAY_FACTOR** (default 0.995) — How fast a swapped-out battery's
  saturation score decays while it has no target. Applied each cycle. Lower
  values let it recover sooner; 1.0 means the battery never becomes eligible
  again.

### Control quality

Everything above is a knob. **Control quality** is the answer they add up to:
one reading that says whether the grid really is being held at zero. It needs no
configuration.

It grades the **average** grid error over roughly the last minute, not the
instant one. Every load step — a kettle, an oven — lands on the meter before any
battery can answer it, so a healthy install still shows large momentary swings.
What marks a working loop is that it comes back. That is exactly why the
allowance for "stable" sits well above the settling band (`BALANCE_DEADBAND`,
floored at 25 W). It is calibrated against the simulated households in
[docs/simulator.md](simulator.md).

| Verdict | What it means |
|---|---|
| `stable` | The grid is being held close to zero. Nothing to do. |
| `off_target` | The grid is not being held at zero, and the batteries still have room to do it. |
| `limited` | Same, but every battery has been out of headroom (full, empty or clamped) for most of the window. Not a control problem. |
| `warmup` | Steering, but not enough samples yet to judge. |
| `idle` | Nothing is being steered: no batteries polling, relay mode, inspection mode, or the meter has been unavailable for over a minute. |

Alongside it, a **score** from 0 to 100 % scales with how far the mean grid
error sits from the band. Trend or alert on the score; read the verdict. While
the loop is `idle` or in `warmup`, the score is **absent** (`unknown` in Home
Assistant) rather than a perfect 100 that nothing has measured yet. So gate a
score-based automation on the verdict, or on the score not being `unknown`.

Both appear as diagnostic entities in Home Assistant (see
[MQTT Insights](mqtt-insights.md#ct002--per-device-status)) and on the
Diagnostics tab of the [dashboard](dashboard.md). So does the evidence behind
them: the mean grid error, the share of time spent inside the band, and the
rate of zero crossings.

#### Why there is no "oscillating" verdict

A loop can miss in two opposite ways. **Hunting** overshoots past zero in both
directions; fix it by *lowering* `BALANCE_GAIN` or `PACE_MAX_STEP`. **Lagging**
never closes the gap; fix it by *raising* them. Naming the wrong one sends you
the wrong way, so AstraMeter does not guess: it reports `off_target` and
publishes the evidence.

The evidence is the **zero-crossing rate**, published beside the verdict on
both the dashboard and MQTT (Home Assistant: *Control Quality Zero
Crossings*). A hunting loop crosses zero again and again at large amplitude. A
lagging one sits on one side and barely crosses at all. Read it together with
the mean error:

- **Crossings near zero, error large** — the loop is not keeping up. Raise
  `BALANCE_GAIN` or `PACE_MAX_STEP`, and check the batteries are not simply at
  their limits (`limited` covers the clear-cut case, but a mixed pool can hide
  it).
- **Crossings frequent, error large** — the loop is overshooting. Lower
  `BALANCE_GAIN`, or lower `PACE_MAX_STEP` so each step is smaller. A slow or
  heavily smoothed powermeter makes this worse: every correction is applied
  against a reading that predates it.
- **A noisy meter also produces frequent crossings** without the loop doing
  anything wrong. That is why this is evidence to weigh, not a verdict.

Before you change anything, look at the house. A kilowatt appliance switching
every minute, in a home that takes ~30 s to settle, leaves the loop permanently
mid-response. `off_target` is then an honest description of the *house*, not a
misconfiguration. An `off_target` verdict that shows up only under surplus
usually means the pool cannot absorb: DC-only batteries cannot charge from AC.

**If it never leaves `warmup`**, the control loop runs slower than the reading
can describe. That happens with a `DEDUPE_TIME_WINDOW` above 60 s, the only
supported way to push corrections that far apart. A loop that corrects once a
minute cannot be graded at any finer grain.

**If it says `limited` most of the day**, nothing is wrong with the steering:
the pack is full, empty, or capped below what the house needs. The score still
reflects tracking accuracy in that state, so alert on the verdict rather than on
the score alone.

## Marstek cloud auto-registration

Optional. Auto-create/check managed fake CT device(s) at startup so the Marstek
app recognizes the emulator:

- **MARSTEK.ENABLE** — auto-create/check managed fake CT device(s) at startup
- **MARSTEK.MAILBOX / PASSWORD** — credentials used to call the Marstek API
- For `ct002` a managed `HME-4` device is ensured, for `ct003` a managed `HME-3`
  device.
- Device fields created by AstraMeter:
  - `devid == mac` (random lowercase hex)
  - `bluetooth_name = MST-SMR_<last4(mac)>`
  - `name = AstraMeter CT002` / `AstraMeter CT003`
- If a matching managed device of the expected type already exists, no new
  device is created.

Important behavior notes:

- Managed fake CT devices appear as **offline** in the app CT list. That is
  expected.
- Refresh the CT device list after registration (or log out and in if needed).
  Then select `AstraMeter CT002` / `AstraMeter CT003`, switch battery mode to
  automatic, and choose that CT. You can select it as soon as it appears in the
  device list.
- Marstek credentials are only needed for the one-time registration. Remove
  `MARSTEK.MAILBOX` / `MARSTEK.PASSWORD` as soon as registration succeeds (or if
  the managed device already exists).
- If you use the Home Assistant app `custom_config`, values from that file
  override app UI fields.
- **Marstek app (optional):** live CT grid power over MQTT uses the same
  `[MQTT_INSIGHTS]` broker as
  [hame-relay](https://github.com/tomquist/hame-relay) **≥ 1.3.5**. See
  [MQTT Insights](mqtt-insights.md#optional-marstek-mobile-app-live-mqtt)
  (optional Marstek subsection). HA entities do not depend on this.
